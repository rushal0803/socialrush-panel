## Minimal evidence procedure — do not execute without approval

1. Prefer an existing authoritative source-controlled creation script or privately held schema-only artifact. Record its repository/path, commit or SHA256, provenance date and owning reviewer. Do not import it automatically; inspect complete types, defaults, keys, indexes, constraints, RLS, grants, triggers, referenced functions/types/sequences and ordering first.
2. If none exists, the owner must explicitly approve **the exact project/database identity**, an existing read-only connection profile, the exact commit/hash of [the catalog-only query](../../scripts/clean-install-schema-evidence-readonly.sql), the two permitted table names, the executor and a private output location. “Continue,” an accessible connector, or an environment-file URL is not approval. No production access is authorized by this document. Do not ask for or paste passwords/keys. Do not create roles, alter grants, change configuration or purchase infrastructure as part of collection.
3. After that approval only, an authorized executor can run `psql -X -v ON_ERROR_STOP=1 -f scripts/clean-install-schema-evidence-readonly.sql` using the approved private connection profile. An owner-operated SQL editor may run the exact reviewed script instead; do not select application tables from its data browser. No connection URI/password goes in command text or shared logs. The script starts a read-only transaction, sets 15-second statement/2-second lock limits, fixes search_path to pg_catalog and rolls back. Stop on errors, unexpected target identity, missing metadata privileges, or unrelated objects; do not silently retry as an administrator.
4. The nine result sections contain target existence/owner/RLS flags; column types/defaults/identity; complete constraint and index definitions; policy expressions; table/column ACLs; trigger definitions/function identities; and dependency identities. It never selects CRM/customer/order/service rows, Auth users, Vault, role passwords, function bodies or migration statement text. Review output privately: even schema expressions/trigger arguments may contain operational identifiers or embedded literals. Redact secrets before sharing; never commit raw remote evidence, credentials or browser sessions to PR artifacts.
5. This inventory is deliberately **not** complete creation SQL. Review identified referenced functions, policies, types/enums, sequences, schema ACLs, role memberships/default privileges, partitions/inheritance and inbound dependencies. Obtain existing source definitions for that small closure first. If additional remote definitions are required, request a second explicit approval naming those objects and queries before collecting them; do not broaden to an all-schema dump. Do not execute customer functions to inspect them.
6. Record identity, collection time, server version supplied by the owner, script hash, completeness/privilege limitations and private artifact hash. Current schema evidence may include later changes; it does not establish the original pre-September migration state or production-upgrade compatibility by itself. Review chronology and provenance before adopting a versioned clean-install foundation plan.
7. Only after valid foundation SQL is reviewed: add the explicit, traceable clean-install prerequisite without editing historical files; rerun every migration in the network-none Actions stack; keep cron disabled and stop at any new failure. Only completed full replay permits actual Next.js Auth/session/admin/customer wallet/manual receipt/refund/history/revenue and mobile/desktop journeys. No production migrations, data repair, merge or deployment follows from evidence approval.
